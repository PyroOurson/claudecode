# F9. Alternative routes

This is a proposal awaiting the owner's approval; nothing in it is built yet. It builds on the exact time-dependent search in `src/route.rs` (B6), the search limits (R5), the shared exploration cache (P2), and the Tier 1 features F2 (attribution list), F3 (waypoints and GeoJSON) and F4 (routing options).

## Goal

Today a request returns one route: the earliest arrival. Travellers often prefer a route that arrives a few minutes later with one change fewer, or with much less walking. F9 returns up to `k` routes, each best at something: the fastest, the one with the fewest changes and the one with the least walking. Further slots are filled with other routes that no returned route beats on all three criteria (the Pareto set of arrival time, changes and walking metres).

Requests without the new field get exactly today's answer, from today's code path.

## API sketch

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `alternatives` | integer, 1 to 5 | absent | Return up to this many routes. |
| `alternatives_slack_min` | integer, 0 to 120 | 30 | Skip routes that arrive more than this many minutes after the fastest. |

```json
{"required_nodes": [1, 2], "time": "20260808T120000", "alternatives": 3}
```

The top-level `route` and `arrival_time` are the fastest alternative, so a client that ignores the new field still works. `...` marks arrays shortened here; every entry carries its own full `route`.

```json
{
  "route": [
    {"mode": "walking", "line": null, "nodes": [1, 3, 100], "departure_time": "2026-08-08T12:00:00Z", "arrival_time": "2026-08-08T12:03:37.555Z"},
    {"mode": "train", "line": null, "nodes": [100, 500], "departure_time": "2026-08-08T12:10:00Z", "arrival_time": "2026-08-08T12:11:00Z"},
    {"mode": "train", "line": null, "nodes": [500, 200], "departure_time": "2026-08-08T12:12:00Z", "arrival_time": "2026-08-08T12:13:00Z"},
    {"mode": "walking", "line": null, "nodes": [200, 2], "departure_time": "2026-08-08T12:13:00Z", "arrival_time": "2026-08-08T12:13:00Z"}
  ],
  "arrival_time": "2026-08-08T12:13:00Z",
  "alternatives": [
    {"criteria": ["fastest"], "arrival_time": "2026-08-08T12:13:00Z", "changes": 1, "walking_m": 300, "route": [...]},
    {"criteria": ["fewest_changes"], "arrival_time": "2026-08-08T12:25:00Z", "changes": 0, "walking_m": 300, "route": [...]},
    {"criteria": ["least_walking"], "arrival_time": "2026-08-08T12:40:00Z", "changes": 0, "walking_m": 0, "route": [...]}
  ],
  "alternatives_complete": true
}
```

- `changes` is the number of vehicle legs minus one (0 for a walk or a direct vehicle). `walking_m` is rounded to whole metres.
- One route that wins several criteria appears once, with all of them in `criteria`. Fill-up routes have `"criteria": []`.
- `"format": "geojson"` (F3) returns one FeatureCollection; every feature gets an `alternative` index property. The F2 `attribution` list covers every plugin used by any returned route.
- `400` for an `alternatives` value that is not an integer from 1 to 5, and, in this first version, for `alternatives` together with `arrive_by` (F10).

## Protocol impact

None. The new search calls `fetch_outgoing` exactly as today, with the same 60 s minimum transfer and the same 5-minute cache windows.

Protocol v2 (F8, not selected) would help in two places. Its `trip_id` would let the server tell a real change from one vehicle that a plugin reports under two line IDs. Its honoured `duration` would let a later label at a station reuse an earlier answer instead of asking again for a later window. The fallback with v1 is to count vehicle legs as listed, and to rely on the per-request `seen` map, the shared cache and `MAPS_MAX_PLUGIN_CALLS`.

## Algorithm

A new function `pareto_search` in `src/route.rs`, next to `a_star_time_dependent`. `route_with_schedule` calls it only when `alternatives` is present.

1. **Shared moves.** Move the code that generates successors (walking edges, station to entrance and entrance to station at 0 s, plugin journeys from a station at arrival + `min_transfer`) out of `a_star_time_dependent` into a helper used by both searches. This refactor must not change behaviour, and the existing tests prove it.
2. **Labels.** An arena `Vec<Label>` holds `Label { node, transit, arrival, boardings: u8, walk_m: u32, parent: u32, edge: TransitionEdge }`. Each state `(node, transit)` keeps a bag `HashMap<StateKey, Vec<u32>>` of non-dominated labels instead of the single `best_arrival` entry. Walking edges add `length_m`, station and entrance moves add 0 m, and a plugin journey adds one boarding.
3. **Dominance.** L1 dominates L2 when its arrival, boardings and walk are all less than or equal. Boardings, not changes, are compared at intermediate states. A walk (0 boardings) and a direct train (1 boarding) both have 0 changes, but after one more vehicle they have 0 and 1 changes, so comparing changes there would drop valid routes.
4. **Order and pruning.** The heap pops labels by arrival + estimate, with the same estimate as today (exact mode by default). A new label is dropped if a label in its bag or a label already at the target dominates it; labels it dominates are marked dead and skipped when popped.
5. **Bag cap.** At most `k + 1` labels per state. When a bag is full, evict the latest-arriving label that is not the bag's minimum on any criterion. The minimum-arrival label is never evicted.
6. **Stopping.** Stop when the popped arrival + estimate exceeds the fastest target arrival + slack, when the heap is empty, or at an R5 limit. If a limit stops the search after the fastest route is found, return what was found with `"alternatives_complete": false`. If no route is found, return today's `404`.
7. **Via nodes.** With more than two required nodes, the target bag of leg *i* seeds leg *i + 1*, and each label keeps its own arrival, boardings and walk. The Pareto set therefore covers the whole trip, and parents point across legs in the shared arena.
8. **Selection.** Filter the target bag on (arrival, changes, walk). Pick the fastest (ties go to fewer changes, then less walking), then the fewest changes (ties go to the earlier arrival), then the least walking (ties go to the earlier arrival). Fill the remaining slots by arrival. Skip a candidate whose sequence of vehicle legs (station, departure, line) equals an already chosen one. Build each route with today's `reconstruct_path` segment rules.

**Why bags stay small.** On a walk with the same history, arrival = start + walk / speed, so the shorter walk also arrives earlier and dominates. Bags grow only where vehicle choices differ.

**Why the fastest is kept.** FIFO holds (waiting is allowed), so the earliest arrival at the target can be reached through earliest-arrival labels only. Those are never evicted, so `alternatives[0].arrival_time` equals today's `arrival_time`. On exact ties, the path may differ from today's.

**F4 options.** `max_walk_m` becomes exact, because walking is part of the label; the single-label search can only approximate it. `transfer_penalty_s` only changes which route is called fastest (arrival + penalty × changes). `exclude_modes`, `min_transfer_s` and `avoid_steps` apply through the shared moves.

## Cost

- **Effort:** M to L, about 5 to 7 days. That is 1 day for the behaviour-neutral refactor, 2 to 3 for the label search and selection, 1 for HTTP, GeoJSON and attribution, and 1 to 2 for tests.
- **CPU (estimates, not measured):**
  - Walk-only: one label per state, so expansions stay close to today's (29,319 states, about 40 ms, for the 9 h 26 min Andorra walk in exact mode). The slack adds the states reachable in 30 more minutes; on a long walk that is perhaps 10 to 20%.
  - With vehicles: at most `k + 1` labels per state, so at most about 4 times today's expansions and time for `k = 3`.
- **Memory:** a label is about 64 bytes. The worst case on Andorra is 37,524 nodes × 4 labels × 64 bytes ≈ 9.6 MB per request. Typical requests use far less, and `MAPS_MAX_EXPANDED` still applies.
- **Plugin calls:** a station is explored once per surviving label instead of once. Labels that arrive within the same 5-minute window reuse the request's `seen` map. The estimate is 1 to 2 times today's calls, at worst `k + 1` times, and `MAPS_MAX_PLUGIN_CALLS` (1000) still caps the request.
- **Dependencies:** none.

## Risks

- **Label explosion** on dense networks. The bag cap, the slack and the R5 limits bound it, and `alternatives_complete: false` tells the client when they cut the search.
- **Drift in normal routing.** The old search stays the default path. The only shared change is the move refactor, which the existing suite and an equivalence test cover.
- **Counting changes without `trip_id`.** A plugin that splits one vehicle run into two line IDs shows a change that is not real. Today's response has the same limitation.
- **Estimate assumptions.** The search inherits exact mode's assumption that no vehicle averages more than `MAPS_MAX_SPEED_KMH` between stations. If a vehicle does, Pareto labels can be missed, just as the fastest route can be today. With `"fast": true`, alternatives are approximate; the README must say so.
- **Compatibility.** The new fields appear only when `alternatives` is sent, and every other request keeps today's response.

## Test plan

These tests use the fixture `tests/fixtures/fixture.osm.pbf` and `tests/fake_plugin.py`, with no Docker, Nix or network.

- **Pareto scenario.** Plugin `train`: `available` `{"100": [3], "500": [], "200": [2]}`, explore `100 → 500` (offset 600, cost 60), `100 → 200` (offset 1200, cost 300) and `500 → 200` (offset 120, cost 60). Plugin `bus`: `{"600": [1], "200": [2]}`, explore `600 → 200` (offset 1800, cost 600). For `[1, 2]` at 12:00 with `alternatives: 3`, expect exactly the three routes in the example, with their criteria, arrivals, changes and walking metres.
- **Dominated route.** The 36-minute walk (12:36:15.553, 3,002 m) is not returned, because the direct train dominates it.
- **One alternative.** With `alternatives: 1`, the top-level `route` and `arrival_time` equal `alternatives[0]`.
- **Equivalence.** For every request in the existing HTTP tests, the Pareto fastest `arrival_time` equals today's. Without `alternatives`, all existing tests pass unchanged.
- **Validation.** `alternatives` values `0`, `6`, `"3"` and `2.5`, and `alternatives` with `arrive_by`, get `400`.
- **Limits.** With `big_network` (200 stations) and `MAPS_MAX_PLUGIN_CALLS=10`, the call log shows at most 10 explore calls.
- **Bag unit tests** on hand-made labels: dominance, eviction that keeps the three minima, and the boardings-versus-changes rule.
- **Via node.** For `[1, 3, 2]`, every label from the first leg seeds the second.
- **GeoJSON.** Every feature has an `alternative` index. With two plugins, the F2 attribution lists only the plugins that the returned routes use.
- **Cache.** A repeated `alternatives` request makes no plugin calls.
