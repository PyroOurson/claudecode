# F13. Graph cache on disk

This is a proposal awaiting the owner's approval; nothing in it is built yet. It builds on the compact graph from P1 (`Graph` in `src/graph.rs`), building the graph at startup (R1, `load_graph` in `main.rs`) and the stable map-file hash from R4 (`overpass::pbf_hash`).

## Goal

Every start rebuilds the walking graph from the `.osm.pbf` files, with two full decoding passes in `Graph::load`. On Andorra this takes about 40 ms, so it does not matter there. On a country-size extract it is expected to take minutes (an estimate; no large region has been measured). Meanwhile the server answers nothing, not even `503`, because the listener binds only after `load_graph` returns.

F13 stores the finished graph on disk, keyed by the R4 hash, so that later starts read it back at disk speed.

F13 does not touch the other slow steps: the first Overpass import, and the plugins' own work during `available`.

## API sketch

There is no HTTP change. Two new settings:

| Variable | Default | Meaning |
| --- | --- | --- |
| `MAPS_GRAPH_CACHE_DIR` | `cache` | Folder for the cache file, relative to the working directory. It is created if missing. |
| `MAPS_GRAPH_CACHE` | `1` | `0` turns the cache off: always build from the map files, and write nothing. |

The startup log says which path was taken:

```
Loading the walking graph from andorra.osm.pbf in /srv/maps/assets...
Read the walking graph from cache/graph-fnv1a-3f9c2a7d10b4e6c1-r1.bin (1.3 MB).
Walking graph ready in 0.0 s.
```

On a miss, it says `No graph cache for fnv1a-3f9c2a7d10b4e6c1-r1, building it from the map files`, and later `Wrote cache/graph-...bin`. F1's `/health` may add `"graph": {"source": "cache"}` or `"map_files"`.

## Protocol impact

None.

## Algorithm

**File format** (little-endian, format version 1):

| Part | Content |
| --- | --- |
| Header | magic `MAPSGRPH`, format version `u32`, key length `u32` and key bytes, node count `u64`, edge count `u64` |
| Sections | `ids` as `i64` × n; `coordinates` as `i32` × 2n; `offsets` as `u32` × (n + 1); `edges` as (`u32` target, `f32` length_m) × m; later, the F4 and F15 flag arrays |
| Trailer | FNV-1a 64 checksum of every byte before it |

**Key.**
- The key is `overpass::pbf_hash(&assets, &files)` (`fnv1a-` plus 16 hex digits over each file's name, size and modification time) plus `-r` and `GRAPH_RULES_VERSION`, a new constant in `graph.rs`.
- The rules version covers the code side: it is bumped whenever `is_walkable`, `is_station_like`, edge lengths or the layout change.
- The file name is `graph-<key>.bin`.

**Read** (`Graph::read_cache(path, key)`, called by `load_graph` before `Graph::from_pbfs`):

1. Check the magic, the format version and the key.
2. Before allocating anything, check that the file size equals what the header counts imply. A corrupt header then cannot cause a huge allocation.
3. Stream each section through a 64 KB `BufReader` into its typed `Vec` with `from_le_bytes`, updating the checksum as it goes.
4. Validate:
   - the checksum matches;
   - `ids` are strictly increasing;
   - `offsets` start at 0, never decrease and end at m;
   - every edge target is below n;
   - every length is finite and at least 0.

   These checks guarantee that `neighbours` and `coords_from_id` can never index out of bounds.
5. On any failure, log the reason, build from the map files, and overwrite the file.

**Write** (`Graph::write_cache`), after building from the map files:
- Write to `graph-<key>.bin.tmp-<pid>` in the same folder, `sync_all`, then rename, which is atomic on POSIX. Then delete any other `graph-*.bin` in the folder.
- The write runs in `spawn_blocking` after the listener is up, so it does not delay startup.
- A failure (read-only or full disk) only logs a warning.

**Guard test.** A digest of the graphs built from `tests/fixtures/fixture.osm.pbf` and `walkability.osm.pbf` is pinned next to `GRAPH_RULES_VERSION`. A change to the walkability rules fails this test until both are updated, so the version cannot be forgotten.

**Helpers.** `fnv1a64` moves from `overpass.rs` into a small shared module, and gains an incremental form for streaming.

**Why not `bincode` or `memmap2`?** `bincode` (with serde) adds a dependency whose format has changed between major versions. `memmap2` would avoid one copy, but needs `unsafe` and a `Graph` that borrows its arrays. The flat format is about 150 lines of std-only code and leaves `Graph` unchanged.

## Cost

- **Effort:** S to M, about 2 to 3 days.
- **File size:** equal to the graph's `heap_bytes` plus about 100 bytes: 1.3 MB on Andorra, about 36 bytes per walkable node elsewhere (the README's rule of thumb).
- **Read time:** bound by the disk and by the element conversion and checksum. Both are expected to run at hundreds of MB/s or more, so a 1 GB graph (about 30 million walkable nodes) would load in a few seconds (estimate), against minutes of decoding (estimate). Both figures should be measured on a large extract during review.
- **Memory:** peak while reading is the graph plus a 64 KB buffer. That is less than building from the map files, which peaks at about 5 MB on Andorra for a 1.3 MB graph.
- **Disk:** one file per set of map files; older files are deleted.
- **Dependencies:** none.

## Risks

- **Stale cache when the rules change** and nobody bumps the version. The guard test catches this.
- **Same-size, same-time file replacement.** A file replaced by a different extract with the same size and modification time (for example, `cp -p` of another snapshot) keeps the old key. This is the same weakness as the R4 Overpass label, which would keep the old import too, so the graph and Overpass stay consistent with each other. Document `MAPS_GRAPH_CACHE=0`, or deleting `cache/`.
- **Corrupt or truncated files** (a crash mid-write, a disk error). Atomic rename, the size check, the checksum and the structural checks turn these into a rebuild, never a panic.
- **Untrusted cache folder.** Whoever can write to it can already change the map files. The bounds checks still stop a crafted file from causing out-of-bounds access or huge allocations.
- **Portability.** The format is little-endian, written explicitly. All supported systems (`x86_64-linux`, `aarch64-linux`, `aarch64-darwin`) are little-endian anyway.
- **Format growth.** F4's steps flag and F15's access arrays must go into the file, and adding them bumps the format version. F3's R-tree is rebuilt from the graph at startup; its cost on a large region is unmeasured, and it could be cached in a later format version.
- **Compatibility.** With the default on, the server creates a `cache/` folder in the working directory, which is a new file on disk and needs a CHANGELOG entry. With `MAPS_GRAPH_CACHE=0`, behaviour is exactly as today.

## Test plan

These tests need no Docker, Nix or network.

- **Round trip.** Build from `fixture.osm.pbf` and `walkability.osm.pbf`, write to a temporary folder and read back. `ids`, `coordinates`, `offsets` and `edges` must be identical (through a test-only `PartialEq`), and the fixture route requests in `tests.rs` give byte-identical responses on both graphs.
- **Keys.**
  - A different key misses.
  - Changing the map file's modification time with `File::set_modified` (stable since Rust 1.75; the MSRV is 1.88) gives a new key and a rebuild, and the old file is deleted.
  - A different `GRAPH_RULES_VERSION` misses.
- **Corruption.**
  - Flipping one byte in each section fails the checksum and falls back to the map files.
  - A truncated file fails the size check.
  - A header claiming 2^40 nodes is rejected before any allocation.
- **Structure.** A hand-made file with a valid checksum but an edge target ≥ n is rejected.
- **Writing.**
  - A read-only cache folder gives a warning, and startup continues.
  - After a successful write, no `.tmp-` file is left.
  - `MAPS_GRAPH_CACHE=0` writes nothing.
- **Startup path.** `load_graph` returns a `GraphSource` (`Cache` or `MapFiles`); the second call on the same folder reports `Cache`.
- **Guard.** The rules digest test fails when the fixture graph changes.
