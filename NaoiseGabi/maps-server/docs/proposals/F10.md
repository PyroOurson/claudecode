# F10. Arrive-by search

This is a proposal awaiting the owner's approval; nothing in it is built yet. It builds on the exact forward search in `src/route.rs` (B6), the search limits (R5), the shared exploration cache (P2), and the Tier 1 features F3 (waypoints) and F4 (`min_transfer_s`).

## Goal

Let a traveller say "I must be there by 12:20" and get the route that leaves as late as possible while still arriving by then. Today the only time a client can set is the departure `time`.

## API sketch

A new optional field, `arrive_by`, uses the same formats as `time` (`YYYYmmddTHHMMSS`, `YYYY-mm-ddTHH:MM:SS`, or RFC 3339 with an offset) and is parsed by `parse_request_time`. It applies to the last required node.

```json
{"required_nodes": [1, 2], "arrive_by": "20260808T122000"}
```

The response has today's shape, plus `departure_time` and `arrive_by` at the top level, which appear only for arrive-by requests.

```json
{
  "route": [
    {"mode": "walking", "line": null, "nodes": [1, 3, 100], "departure_time": "2026-08-08T12:10:22.445Z", "arrival_time": "2026-08-08T12:14:00Z"},
    {"mode": "train", "line": null, "nodes": [100, 200], "departure_time": "2026-08-08T12:15:00Z", "arrival_time": "2026-08-08T12:20:00Z"},
    {"mode": "walking", "line": null, "nodes": [200, 2], "departure_time": "2026-08-08T12:20:00Z", "arrival_time": "2026-08-08T12:20:00Z"}
  ],
  "departure_time": "2026-08-08T12:10:22.445Z",
  "arrival_time": "2026-08-08T12:20:00Z",
  "arrive_by": "2026-08-08T12:20:00Z"
}
```

Errors:

- `400` when both `time` and `arrive_by` are sent, when `arrive_by` does not parse, or, in this first version, for `arrive_by` with `alternatives` (F9).
- `404` with `{"error": "no route arrives in time", "arrive_by": "...", "earliest_arrival": "..."}` when the earliest possible arrival is too late. `earliest_arrival` comes from the probe that leaves `MAPS_HORIZON_H` before `arrive_by`.
- Today's `{"error": "no route", "failed_leg": [...]}` and `{"error": "no route within limits", "limit": ...}` keep their meaning.

One new setting, `MAPS_ARRIVE_BY_MAX_PROBES` (default 12), caps the forward searches per request.

## Protocol impact

None with the design below.

An exact reverse search would need the plugins to answer "which journeys arrive at station S before time T". The v1 protocol only has `explore`, which lists departures. That question would be a new action announced as a capability in protocol v2 (F8, not selected).

This proposal uses repeated forward searches instead, which work with every v1 plugin unchanged. Plugins see more `explore` calls at nearby times, and the cache absorbs most of them. If v2 is approved later, the HTTP API stays the same and only the algorithm changes.

**The reverse search, for reference.** The walking graph is symmetric (`Graph::build` stores both directions of every way), and station-to-entrance moves cost 0 s both ways. A backward search would therefore reuse `graph.neighbours` unchanged and keep one latest departure per state, mirroring today's one earliest arrival per state.

## Algorithm

A new function `route_arriving_by` in `src/route.rs` wraps `route_with_schedule`. Let EA(t) be the arrival of a forward search that leaves at t. Waiting is always allowed, so EA never decreases as t grows (FIFO). The search looks for the latest t with EA(t) ≤ T.

1. **Upper bound.** t_hi = T − LB, where LB is the straight-line lower bound summed over the legs: `heuristic_seconds` in exact mode, at `MAPS_MAX_SPEED_KMH`. No departure after t_hi can arrive by T. The first probe is at t_hi, and if it is feasible, the search is done.
2. **Back off.** Probe at t_hi − 10 min, then −20, −40, and so on, doubling, until a probe is feasible or the step passes `MAPS_HORIZON_H`. Every infeasible probe lowers t_hi.
3. **Tighten.** A feasible probe at t returns route R. R stays feasible if the traveller leaves later, as long as they still reach its first vehicle:
   - shift = (first vehicle departure − min transfer) − (arrival at that vehicle's station);
   - for a walk-only R, shift = T − EA(t).

   The lower bound becomes t_lo = t + shift, the latest departure for R itself.
4. **Bisect** between t_lo and t_hi until they are 60 s apart, tightening after every feasible probe.
5. **Answer.** Return R from the last feasible probe. Everything before its first vehicle moves later by the shift, and the rest keeps its times. The result is the latest departure for that route, and no other route can leave more than 60 s later.
6. **Bounds.** All probes share one `SearchStats` and one `fetch_outgoing` closure (with its `seen` map), so `MAPS_MAX_EXPANDED` and `MAPS_MAX_PLUGIN_CALLS` cap the whole request. A probe that a limit stops counts as infeasible, and so does the rest of the search once the probe cap is reached. If no probe was feasible, the limit error is returned as today.

`route_arriving_by` takes the probe as a closure, so the bisection can be unit-tested on a synthetic EA function without a graph. In `http.rs`, `parse_request` fills a new `RouteRequest.arrive_by: Option<DateTime<Utc>>`, and `compute` picks the function.

**Interactions:**

- **Via nodes.** EA through `route_with_schedule` chains the legs and stays monotone, and the shift applies to everything before the first vehicle, across legs.
- **`"fast": true`.** EA is not exact in fast mode, so monotonicity can break. The search still ends, but it may miss the latest departure; the README must say so.
- **F4.** `min_transfer_s` is used in the shift.
- **F11.** Isochrones stay forward-only.

## Cost

- **Effort:** S to M, about 2 to 3 days. That is 1 day for `route_arriving_by` and its unit tests, 0.5 for HTTP, and 1 for fixture tests and the fake-plugin extension.
- **CPU (estimates, not measured):** one arrive-by request costs as much as its probes. For a trip of about an hour, back-off takes 3 to 5 probes and bisection with tightening 3 to 5 more, so about 6 to 10 forward searches. The cap is 12.
- **Plugin calls:** probes ask the same stations at times minutes apart, and 5-minute windows mean many probes hit the request's `seen` map or the shared cache (TTL 120 s). The estimate is 1.5 to 3 times a single search's calls, still capped by `MAPS_MAX_PLUGIN_CALLS` (1000).
- **Memory:** one probe runs at a time, so memory is the same as one search today.
- **Dependencies:** none.

## Risks

- **Changing data during a request.** A cache entry that expires, or realtime data that changes between probes, can make EA non-monotone for that request. The bisection still ends, and the answer is still feasible for the data it was computed from.
- **Window artefacts.** The fake plugin's `offset` places a departure relative to the requested window start, so its timetable moves with the window. Real timetables do not, and tightening relies on that. Tests therefore need fixed departure times (see Test plan).
- **Plugin load.** Up to 12 probes per request. The cache, the shared call limit and F16's per-IP plugin-call budget bound it.
- **Compatibility.** Requests with `time`, or with neither field, run exactly as today. The new fields appear only for `arrive_by` requests.
- **Resolution.** Another route may leave up to 60 s later than the one returned. The probe cap and the 60 s step can be tuned once real request logs exist.

## Test plan

These tests use `tests/fixtures/fixture.osm.pbf` and `tests/fake_plugin.py`, with no Docker, Nix or network.

- **Fake plugin.** Add an optional `at` field (an absolute `YYYYmmddTHHMMSS` departure) next to `offset`. A leg with `at` is listed only if it departs at or after the requested window start, like a real timetable.
- **Train.** A fixed train `100 → 200` at 12:15, cost 300, with `arrive_by` 12:20 for `[1, 2]`: the departure is 12:10:22.445 (300 m at 1.38 m/s, plus the 60 s transfer) and the route is the one in the example.
- **Too late for the train.** With `arrive_by` 12:19:59, the train is too late, so the answer is the walk, leaving at exactly 12:19:59 − 36 min 15.553 s.
- **Round trip.** For several `arrive_by` values, a forward request with `time` = the returned `departure_time` arrives at or before `arrive_by`.
- **Bisection unit tests** on step functions: a step at the answer, many steps, all infeasible, the probe cap reached, and a limit error on one probe.
- **Validation.** `time` together with `arrive_by`, an unparsable `arrive_by`, and `arrive_by` with `alternatives` get `400`.
- **No route.** With `MAPS_HORIZON_H=0.5` and only the train, an `arrive_by` before the train's arrival gets `404` with `earliest_arrival`.
- **Limits.** With `big_network` and `MAPS_MAX_PLUGIN_CALLS=10`, the call log shows at most 10 explore calls over all probes, and a repeated identical request makes no plugin calls.
- **Probe cap.** With `MAPS_ARRIVE_BY_MAX_PROBES=2`, the response is still feasible (arrival ≤ `arrive_by`).
