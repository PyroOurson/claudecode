# F11. Isochrones

This is a proposal awaiting the owner's approval; nothing in it is built yet. It builds on the time-dependent search in `src/route.rs`, the search limits (R5), the shared exploration cache (P2), and the Tier 1 features F2 (attribution list), F3 (waypoint snapping and GeoJSON) and F4 (routing options).

## Goal

Show everywhere a traveller can reach from one place within N minutes, by walking and public transport. Typical uses are "where can I live within 30 minutes of work" maps, and checking how well an area is served. The answer gives exact arrival times for the reachable walkable nodes and stations, plus an outline polygon for drawing.

## API sketch

`POST /isochrone` takes these fields. `OPTIONS /isochrone` is answered like `OPTIONS /`, and other methods get `405`.

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `from` | OSM node ID, or `[lat, lon]` | required | A `[lat, lon]` start is snapped as in F3, within `max_snap_m`. |
| `time` | string | now | Same formats as `POST /`. |
| `max_minutes` | integer, 1 to `MAPS_ISOCHRONE_MAX_MINUTES` | required | New setting, default 120. |
| `walking_speed` | number | `0.00138` | Same range as `POST /`. |
| `nodes` | `"all"`, `"stations"` or `"none"` | `"all"` | How much of the node list to return. |
| `resolution_m` | integer, 25 to 500 | 50 | Grid cell size of the outline. |
| F4 options | | | `min_transfer_s`, `exclude_modes`, `avoid_steps`. |

`max_walk_m` gets `400`: it needs walking distance in the search label (see F9). `fast` is ignored, because a search with no target uses no estimate.

```json
{"from": 1, "time": "20260808T120000", "max_minutes": 10}
```

```json
{
  "from": {"node": 1},
  "time": "2026-08-08T12:00:00Z",
  "max_minutes": 10,
  "complete": true,
  "nodes": [[1, 0.0, 0.0, 0], [3, 0.0, -0.0027, 218]],
  "stations": [],
  "hull": {
    "type": "Feature",
    "properties": {"max_minutes": 10, "resolution_m": 50},
    "geometry": {"type": "MultiPolygon", "coordinates": [[[[-0.0036, -0.0009], [0.0075, 0.0], [-0.0036, 0.0009], [-0.0036, -0.0009]]]]}
  }
}
```

The hull coordinates are shortened here.

- `nodes` entries are `[id, lat, lon, seconds]`: whole seconds after `time`, rounded up. Arrays keep the list compact, at about 40 bytes per node.
- `stations` lists the reached stations as `{"id", "seconds", "modes"}`. A station without its own coordinates uses its first entrance's, as `position` does in `route.rs`.
- GeoJSON uses `[lon, lat]` (RFC 7946), while `nodes` keeps F3's `[lat, lon]` order. The README must say so.
- A search stopped by an R5 limit answers `200` with `"complete": false` and `"limit": "max_plugin_calls"` (or the limit's name), because a partial map is still useful. The other choice, `404` as for routes, is for the owner.
- `MAPS_ISOCHRONE_MAX_NODES` (default 100,000) caps the list. Beyond it, `nodes` is omitted and `"nodes_truncated": true` is set.
- Errors: `400` for bad fields, `404` for an unknown `from` node, plus `413` and `503` as today. The `Attribution` header and the F2 list credit OpenStreetMap and every plugin whose journeys improved an arrival.

## Protocol impact

None. An isochrone has no target to steer towards, so it explores every station it reaches, which means more `explore` calls than a route. `explore_many` batching in protocol v2 (F8, not selected) would cut round trips. The v1 fallback is today's parallel per-plugin calls (`explore_all`), the shared cache and `MAPS_MAX_PLUGIN_CALLS`.

## Algorithm

**1. Search.** A new function `reachable` in `src/route.rs` reuses the move generator shared with `a_star_time_dependent`: walking edges, station and entrance moves at 0 s, and plugin journeys at arrival + `min_transfer`. If F9 lands first it already contains this refactor; otherwise F11 does it.
- The estimate is 0 (Dijkstra). The search stops popping when the arrival passes `time + max_minutes`, and keeps no `predecessors` map, because no paths are returned.
- One earliest arrival per state is exact, as for routes. A node's time is the earlier of its walking and transit states.

**2. Plugin calls.** The `fetch_outgoing` closure in `compute` (`http.rs`) moves into a helper that both `POST /` and `POST /isochrone` use, so the `seen` map, the cache and the per-plugin parallel calls behave identically.

**3. Outline** (new module `src/hull.rs`):
- **Project.** Map points to metres on a plane around `from` (equirectangular: x = R·Δlon·cos lat₀, y = R·Δlat).
- **Mark cells** of `resolution_m` in a sparse `HashSet<(i32, i32)>`.
  - Each reached walkable node with remaining time r marks the cells within min(r × walking speed, 100 m).
  - Each graph edge leaving a reached node marks the cells along the part walkable in the remaining time. Partly walked edges count, and long edges leave no gaps.
- **Trace** the marked region with marching squares into closed rings, using one fixed rule for saddle cells so rings never cross. Outer rings run counter-clockwise and holes clockwise, as RFC 7946 asks. Islands around stations reached by vehicle become separate polygons of one `MultiPolygon`.
- **Simplify** each ring with Douglas–Peucker at `resolution_m / 2`, then convert back to `[lon, lat]`.

**Why not one concave hull of the points** (for example, the `geo` crate's `ConcaveHull`)? It joins islands around distant stations through land that cannot be reached, its concavity parameter needs tuning for each node density, and it adds the `geo` dependency tree. The grid outline also respects the walking time left at each point.

**4. Output.** Sort `nodes` by ID, then build `stations` and the hull, then apply `nodes` and the node cap.

## Cost

- **Effort:** M, about 4 to 5 days. That is 1 day for the move refactor and `reachable`, 2 for `hull.rs`, and 1 to 2 for HTTP and tests.
- **CPU (estimates, not measured):**
  - Search: there is at most about one walking state per node. The whole of Andorra is 37,524 nodes, and the exact-mode 9 h 26 min walk expanded 29,319 states in about 40 ms. An isochrone covering all of Andorra should take roughly the same, and a 30-minute isochrone in a town, far less.
  - Outline: about 13 cells per reached node at 50 m cells with a 100 m buffer, many shared between nodes. That is at most about 0.5 million cells on Andorra, about 10 MB at peak, and tens of milliseconds.
- **Plugin calls:** one per reached station per serving plugin. A 60-minute isochrone in a large city can reach hundreds of stations, so `MAPS_MAX_PLUGIN_CALLS` (1000) matters here, and F16 should charge isochrones by their plugin calls.
- **Response size:** about 1.5 MB if every Andorra node is reached with `"nodes": "all"`. `"stations"` or `"none"` keeps it small.
- **Dependencies:** none. Marching squares and Douglas–Peucker are about 200 lines.

## Risks

- **Plugin load and API quotas.** Isochrones are the most expensive request type. They are bounded by the limits, the cache and F16. A separate `MAPS_ISOCHRONE_MAX_PLUGIN_CALLS` can be added if the owner wants a tighter cap than for routes.
- **Partial results** must be shown as partial; clients get `complete` and `limit`.
- **Outline accuracy.** The 100 m buffer stands in for walking off the network, and it can cover water or private land. The outline is for display; `nodes` holds the exact data.
- **Projection error.** It grows with distance from `from`: about 2% at 150 km at 45° latitude (from the cosine ratio). That is fine for display.
- **Compatibility.** This is a new path only: `POST /isochrone` answers `404` today, and other endpoints are unchanged.

## Test plan

These tests use `tests/fixtures/fixture.osm.pbf` and `tests/fake_plugin.py`, with no Docker, Nix or network.

- **Walk only.** From node 1 at 12:00 for 10 minutes: `nodes` is `[[1, 0.0, 0.0, 0], [3, 0.0, -0.0027, 218]]` and node 2 is absent. The outline is one polygon from about 100 m west of node 3 to about 828 m east of node 1 (600 s × 1.38 m/s), within one cell.
- **With a train.** Using `train_behind_start` (station 100 at node 3, then 200 at node 2) for 20 minutes: node 2 is reached at 900 s, `stations` lists 100 and 200, and the hull is a `MultiPolygon` with two polygons.
- **Snapping.** `from` as `[lat, lon]` snaps through F3, and a start 600 m away gets `400`.
- **Validation.** `max_minutes` values `0`, `1000` and `"x"`, and `max_walk_m`, get `400`. An unknown node gets `404`. `GET /isochrone` gets `405`, and `OPTIONS /isochrone` returns the same headers as `OPTIONS /`.
- **Limits.** With `big_network` and `MAPS_MAX_PLUGIN_CALLS=10`, the answer is `200` with `complete: false`, `limit: "max_plugin_calls"`, and exactly 10 explore calls in the log.
- **`hull.rs` unit tests** without a graph:
  - one cell gives one closed counter-clockwise square;
  - a ring around an empty cell gives a clockwise hole;
  - two distant cells give two polygons;
  - both saddle cases give non-crossing rings;
  - Douglas–Peucker keeps the endpoints.
- **GeoJSON validity.** Every ring is closed with at least 4 positions, and longitudes and latitudes are in range.
- **Response shape.** `nodes: "stations"` and `"none"` shapes are correct, `MAPS_ISOCHRONE_MAX_NODES=1` sets `nodes_truncated`, and a repeated request makes no plugin calls.
